## 1. Current foundation and audit findings

The current device protocol exchanges snapshots with operation receipts and expected-version checks. `Application/Documents/DocumentSyncService.cs:MutateAsync` uses a serializable transaction, locks `DocumentSyncClocks`, deduplicates operations by owner/operation ID and request hash, and rejects competing versions. `ApplyUploadAsync` replaces page content and removes pages omitted from the incoming aggregate. This preserves conflicts but cannot merge concurrent typing.

The current web path is also a full-content replacement. `WriterApp.Client/Components/Editor/PageEditor.razor:SaveContentAsync` selects either `PUT api/pages/{pageId}` or the scene-content endpoint. A collaborative editor extension alone would leave both overwrite paths active.

Authoring sources are `WriterApp.Client/src/tiptap-editor.ts` and `src/device-editor.ts`; generated JavaScript is not the integration source. The Vite configurations publish a web IIFE and device ES module through `atomic-editor-output.mjs`, with ProseMirror package deduplication. The old root `wwwroot/js/tiptap-editor.js` is not evidence of the active dependency version. The current client package pins Tiptap 3.31.3.

The web editor sends HTML through `OnEditorContentChanged`; device `onUpdate` calls `OnContentChanged` with HTML and an editor version. Both have full-content reset APIs. Those callbacks must become projections/UI notifications in collaborative mode, never another transport for saving shared text.

`WriterApp.Shared/Editor/content-contract.json` is version 2. It supports paragraphs, headings, lists, block quotes, code, images with asset identities, tables, alignment and indentation, and supported marks/link schemes. Contract version 2 is not itself a Yjs protocol version or a complete fingerprint of extension behavior. Custom extension attributes and normalization must be compared between hosts before migration.

`Program.cs` configures SQLite through `AppDbContext`, or SQL Server through `SqlServerMigrationsDbContext`, plus separate migration histories. It registers web identity handlers and native bearer authentication. Authorization currently depends on owner predicates in repositories/controllers; it is not a reusable shared-project membership policy yet.

`DeviceSyncJournal` scopes its file journal by hashed backend and owner and writes through `AtomicDocumentWriter`. `DeviceAuthentication.Generation` fences changed sessions. `LocalEditorSession`, `LocalDocumentRepository`, and `Storage/FileLocalDocumentStore` own native local edits/recovery. Web `EditorSaveCoordinator` writes recovery drafts through `RecoveryDraftService` and localStorage. These preserve snapshots today, not a durable Yjs outbox. Desktop, iOS, and Android hosts exist; iOS and Android already expose resume/background lifecycle hooks. Android is present in this dirty checkout, including untracked host files, and must not be omitted based on the older proposal.

No AGENTS.md was found in the checked workspace, docs directory, or filesystem ancestors. The checkout contains substantial unrelated edits and untracked Android work. Prompt 1 adds only its two documentation files.

## 3. Architecture and ownership decisions

Use one Y.Doc per existing PageId, with the rich-text fragment named `default`. A room key is `environment/documentId/pageId/generation`; the server derives/validates every component, including the page's document/project relationship. Names and client claims grant no permission. Subscribe only to active pages; do not hydrate an entire novel on mobile.

The .NET application owns identity, entitlement, membership, document/page lifecycle, all relational schema migrations, the update ledger/receipts, projections and audit. Add `Application/Collaboration`, shared DTOs under `WriterApp.Shared`, and EF records under `Data/Collaboration` in later prompts. Node owns Yjs decoding/validation, live rooms and WebSockets in a proposed `WriterApp.Collaboration` service. Node accesses persistence through authenticated private .NET endpoints, not a second ORM/schema or a browser-accessible database credential.

Start with one Node instance and one active writer per room. Use a database-backed lease/epoch per room, checked in every commit, so a restarted or overlapping deployment cannot commit as the old room owner. A per-room queue orders edits, compaction and lifecycle barriers; database serialization remains required across .NET and Node. Reject an expired epoch rather than allowing split-brain writes. Scale-out and Redis are deferred until P10 evidence justifies a separate design.

WebSocket traffic uses TLS through the reverse proxy. Internal persistence uses service-to-service credentials (managed identity or scoped rotating credentials), an explicit service audience, request size limits, and private ingress. Browser tickets never authorize internal persistence calls. Do not trust externally supplied EasyAuth-style headers; use existing validated identity resolution to mint tickets.

Store collaboration mode and migration state on the existing `Documents` row, and use separate additive `CollaborationPages`, `CollaborationUpdates`, `CollaborationReceipts`, `CollaborationSnapshots`, `CollaborationOutboxEvents`, and migration-job records. ### Commit-before-apply protocol

Hocuspocus supplies transport and Yjs integration, but its normal debounced `onStoreDocument` hook is not a per-update durable acknowledgement. Use a custom protocol adapter rather than displaying cloud-save status from provider events.

1. Client local Y.Doc generates an update. Atomically persist its immutable envelope to IndexedDB (web) or a native update journal before reporting `Saved on this device`. Keep it pending until its receipt is durable locally.
2. Send an application `commitUpdate` envelope over the authenticated stateless channel. Disable default provider transmission of uncommitted Yjs sync-step-2/update frames; server rejects such inbound writes, including on initial reconnect. Allow read-only state-vector requests and server-to-client synchronization. Enforce the same restriction for malicious/manual clients, not just the UI adapter.
3. Queue by room, recheck session access and validate size/schema/update against a temporary copy of the committed Y.Doc. Persist through .NET with the lease epoch and predecessor sequence. If validation/persistence fails, do not mutate or broadcast the canonical room. Bound unresolved dependencies; replay missing local envelopes in persisted order and reject unsupported schema rather than stripping it.
4. .NET atomically appends update + receipt, increments sequence and writes a projection-work outbox event. It serializes with mode, lifecycle and membership changes. A retry returns the prior receipt without another append.
5. After commit, Node applies the update to the room, broadcasts committed state, and sends the durable receipt. A crash after commit but before apply/receipt is recovered by ledger replay. On apply failure quarantine/reload the room; do not acknowledge writes from an unverified in-memory state.
6. Originating client marks that exact envelope acknowledged. UI distinguishes local durability, pending remote commit, remote durability, and projection freshness.

P3/P5 must verify the exact pinned provider and server message boundaries for this adapter, including initial sync, sync-step-2, read-only sessions, stateless callbacks, and error paths. If those boundaries cannot be enforced with the supported API, implement an explicit transport extension before enabling the feature; do not fall back to debounced persistence. This is a design choice, not a claim that stock Hocuspocus already implements this protocol.

## 5. Write fences, migration and projections

P2 adds a centralized mode/lifecycle guard within transaction boundaries. A check only at a controller entrance is racy. All writers of the same document must participate in a common serialization mechanism compatible with SQLite and SQL Server; migration takes that barrier before changing mode. Add guarded repository/application services and an EF persistence backstop for tracked page writes; direct SQL/bulk operations require explicit guards too. Existing `Sync_*` database triggers must remain accounted for: projection writes currently advance snapshot sync versions. Collaborative clients must not interpret those notifications as an instruction to upload/download replacement snapshots.

Only an internal projection writer can update derived page HTML in collaborative mode. Its capability is an internal service boundary, never a body/header bypass flag. P2 rejects compound legacy aggregate uploads wholesale. P6 introduces a separate metadata/lifecycle route for migrated documents if needed; metadata does not sneak through a full snapshot upload.

Migration sequence: owner requests opt-in against an expected legacy version; preserve local pending writing first; under the barrier set `Migrating` and capture source snapshot/hash/schema; create new per-page generations and seed each Y.Doc exactly once through the common schema adapter; persist baseline snapshots, receipts/job progress, and checked projections; atomically activate only when every page is consistent with the captured source. Failures retain the fence and job progress. Retry resumes by job/page identity without duplicating seed content. No real manuscripts are converted during implementation.

Projection consumers use commit watermarks. Export and AI preparation request a vector of required page/generation sequences and the document structure revision; wait for consistent projections or return pending/retry. They must not silently mix an old page with current structure. Search may be eventually consistent with observable lag. Scene mirrors aggregate ordered page projections, never write back into their source. Update goal/session attribution once per authenticated originating action rather than per receiving client. Keep AI approval/history receipts linked to committed update IDs; delay enabling an AI action whose history/recovery semantics are unsupported.

A feature-disable switch stops new sessions/writes and leaves collaboration state intact/read-only. It must not flip existing collaborative documents to `Legacy` or re-enable stale snapshot writes. Recovery from a checkpoint is a new edit or explicitly new generation, never an invisible HTML reset underneath connected clients.

## 6. Local storage, compatibility and collaboration scope

Web uses y-indexeddb for Y.Doc persistence plus an application envelope/receipt outbox; make local Yjs storage and outbox recovery consistent, including crashes between their writes. A single application-owned IndexedDB transaction/journal may be needed. A cached document alone does not establish that all its updates have durable remote receipts. Snapshot recovery drafts remain a fallback for legacy mode.

Native hosts use a binary update journal with atomic persistence through the shared native storage boundary. Persist continuously; background/suspend callbacks are best-effort and cannot be the only save trigger. Stop old-account sessions before adopting another account; reuse `DeviceAuthentication.Generation` to reject late callbacks. An offline open requires a known compatible local schema/generation. Never re-seed from HTML when reconnecting an established collaborative page.

P8 introduces manuscript-scoped membership with owner/editor/viewer, inherited only by explicitly linked manuscript resources. A project container may contain private supporting documents: granting manuscript access must not expose all project content. Use centralized resource resolution for page, scene, attachment, search, export and AI context. Scope search/AI queries before retrieving content. Invitations bind to verified accepting identity, expire, and cannot be replayed. Membership revision changes serialize with commits; invalidation disconnects sessions and pre-commit checks reject stale credentials. Offline revoked writing remains a private local recovery copy. Offline data already held by a collaborator cannot be remotely erased by revoking server access.

P9 adds ephemeral authenticated presence and comments. Presence payloads cannot spoof another member's identity or write durable content. Comments store relative positions, page generation, author identity, thread state and access-controlled bodies. Existing integer-offset annotations need a verified mapping against the migration snapshot, otherwise mark detached rather than guessing. Collaborative undo tracks local transaction origins; redo must never reverse a remote author's independent edits.

## 10. Prompt 2 implementation decisions and limits

Implemented additive document mode/state columns and six collaboration tables in both EF models/migrations. Generation-scoped keys, independent receipts, bounded indexed strings, binary payloads, lease/commit concurrency tokens, sequence constraints and projection watermarks are present. This is a persistence foundation, not a functioning commit service. Migration jobs retain their source version/hash and recovery snapshot; no migration/job execution endpoint exists.

The authenticated owner-scoped `GET /api/documents/{documentId}/collaboration/capabilities` endpoint reports mode, migration state, permissions and page-generation/schema/protocol/watermark metadata, with diagnostics for incompatible schemas or generations. `FeatureAvailable` and `CanWriteCollaboratively` remain false even for matching clients. Legacy documents retain their ordinary write capability unless archived/trashed. Unknown/ambiguous page state never grants collaborative write permission. Editor pre-open integration belongs to P3/P6; existing clients receive structured conflicts when attempting protected saves.

Enforcement has three layers: a global MVC route-resource precheck and exception mapper; a central tracked-write backstop in every AppDbContext SaveChanges overload; and database fences on Documents, Pages, Sections, DocumentOutlineNodes, DocumentOutlines, DocumentSynopses, Projects, ProjectNodes and SceneContents. Snapshot sync checks document mode within its existing transaction before applying an upload. AI keeps and project/document deletion also perform explicit checks before text/history or bulk-deletion work. Old and new row ownership are both checked when a row is reparented. Unrelated/raw SQL cannot bypass the database fence by skipping EF.

SQLite enforces the fence in BEFORE triggers under its writer serialization. SQL Server AFTER triggers lock affected existing Documents rows with UPDLOCK/HOLDLOCK, including legacy rows, serializing writes against mode transitions. SQL Server restrictive FKs may reject a delete before an AFTER fence runs; the HTTP precheck still supplies the actionable collaboration error. Mode-only forward transitions are reserved for future internal migration code, with no public endpoint; mode downgrades and mode-plus-legacy-field mutations are rejected. During this phase, even title/structure/lifecycle changes are conservatively blocked for protected manuscripts. Project/tree/scene checks also conservatively fence a project containing protected writing; finer-grained safe metadata operations need explicit later commands.

There is no projection writer or internal bypass in P2. An internal projection/migration capability must be implemented in a new fence version and migration when the relevant P5/P7 invariants can be enforced. Editing the frozen P2 trigger installer would change historical migration behavior and is not an acceptable way to introduce that capability. Privileged abort/reset is therefore unavailable now, including for failed conversion. Feature disable never reopens legacy writes.

The SQLite migration adds mode/state columns with named inline constraints through ALTER TABLE rather than rebuilding Documents, preserving existing Sync_* triggers and sync identities. Rollback refuses non-legacy documents or retained collaboration page/job records. When all collaboration state is empty, rollback/re-upgrade preserves legacy text and working sync triggers. Future SQLite table rebuilds must explicitly preserve/reinstall both sync and collaboration triggers.

## 11. Prompt 3 editor module and transport boundary

`WriterApp.Client/src/collaboration/session.ts` is the common editor binding included in both shipped bundles. The web entry exposes `window.tiptapEditor.collaboration`; the device module exports `collaboration`. The canonical content schema and strict source validation are in `editor-schema.ts` and `editor-content.ts`, shared with existing device editing and conversion/AI preview consumers. The legacy web editor keeps its additional formatting extensions; unsupported rich web content must not be silently normalized into the collaborative schema.

`getSupport()` hashes the shared contract, ordered schema node/mark definitions, explicit schema revision and Tiptap version using SHA-256. Compatibility is checked before editor allocation or binary-state application. The raw Yjs-to-JSON conversion is validated before ProseMirror parsing can discard unknown content. The schema removes default Tiptap link-title and ordered-list-type attributes absent from Prosa's contract; authored values for these unsupported attributes remain rejected. All named ProseMirror runtime modules are pinned and deduplicated with Yjs and y-tiptap.

`readCapabilities(identity, signal)` performs the P2 authenticated same-origin GET with page/generation/schema/protocol query parameters. `createLiveEditor` consumes that response (or a response passed by a native .NET host), validates access and exact page identity, and then refuses to mount: P3 has an independent disabled live gate until later authenticated transport, durable commit and migration prerequisites are implemented. Failed or stale capability lookup never falls back to a writable collaborative editor. Existing legacy authoring UI is not migrated or replaced by this step.

`createIsolatedSeed` converts synthetic supported content once to binary Yjs state. `createIsolatedEditor` only accepts the explicit `isolated` environment, a full document/page/generation identity, matching schema support and a checked binary seed. It creates a Y.Doc binding for the active page, disables StarterKit undo history in favor of collaboration-local history and emits separate `onLocalUpdate` and UI-only `onProjection` callbacks. Neither callback acknowledges durability. `receive` checks identity/support, validates against a temporary merged document and applies the update to Yjs with remote origin. Reordered/duplicate updates converge without creating a new local outbound update. No WebSocket/provider or snapshot save is involved.

The binding rejects full-content reset through its wrapper and Tiptap setContent command. The legacy web setContent entry also rejects a collaborative editor. Page switching on the same host disposes the prior binding; destroy removes update listeners, destroys editor/Y.Doc, clears the host and is idempotent. Invalid new state is rejected before disposing the existing active binding. These boundaries must remain when host UI and durable transport are introduced.

Prompt 3 verifies 15 independent-page collaboration browser checks using actual shipped web/device bundles, 109 existing editor browser checks and 50 .NET collaboration/content/editor checks. Browser evidence covers local-user undo/redo, selection preservation, binary-state compatibility, concurrent typing/formatting/deletion, reordered updates, no transport echo or network writes, capability lookup/gates and cleanup. It does not establish native WebView/physical-device support, crash persistence, provider interception or cloud save reliability. Hocuspocus provider 4.7.1 is pinned but not instantiated; P4/P5 must validate its exact authentication and protocol hooks without allowing default inbound sync-step-2/update traffic to bypass durable commit.

## 12. Prompt 4 implementation: authenticated read transport

`WriterApp.Collaboration` is a separately locked Node 24 service using Hocuspocus server/provider 4.7.1 and Yjs 13.6.33. It is excluded from .NET default item discovery. The service validates page-scoped tickets through dedicated internal .NET authorize/bootstrap endpoints. Account authentication, owner access, active paid entitlement, account deletion, manuscript lifecycle, generation and schema checks stay in .NET. Browser Origin and URL checks run before upgrade; native clients without an Origin still require a valid ticket. Defaults disable .NET sessions and bind Node to loopback.

The concrete ticket format is an opaque, authenticated-encrypted ASP.NET Data Protection payload with a read-only purpose and environment discriminator, rather than a JWT with a signing key shared with Node. Node possesses only a separate service-to-service credential. The ticket binds environment, owner, document, page, generation, installation, protocol, content contract, schema, expiry and session version. Five-minute expiry and durable `CollaborationSessions` rows in both database providers support revocation across backend instances. Atomic initial acquisition binds one ticket version to one server-generated socket UUID. Owner refresh atomically advances its version, clears the connection binding and renews expiry; reconnect uses that new ticket. In-band token replacement is rejected. A consumed ticket cannot reconnect after disconnect or service restart without owner refresh.

The two sealed session controllers have a narrow exemption from the P2 content-write filter because they only manage credentials and read committed binary state. Their own authorization remains mandatory; no content/structure controller gains a bypass. P2 storage fences, capability write denial and P3 `createLiveEditor` refusal remain in place. Sessions cannot opt a legacy document into collaboration.

Bootstrap reads a checked snapshot and contiguous committed tail in a serializable transaction. It verifies SHA-256 hashes and a 4096-update/16 MiB binary bound. Missing/inconsistent history fails closed. Node decodes into a temporary Y.Doc and rejects unresolved dependencies before adopting its state. Bootstrap does not regenerate content from page HTML. The provider used by tests is explicitly attached with awareness disabled; provider synchronization grants no durable-save acknowledgement.

Before any established-session message is handled, the raw gate permits only read sync-step-1 requests, exact empty sync-step-2 acknowledgements, awareness queries and close. Nonempty sync-step-2 and normal Yjs updates are refused before mutation, along with awareness writes, stateless/broadcast messages and token sync. Frames are capped at 1 MiB and malformed/trailing bytes are rejected. Hocuspocus read-only scope is an additional safeguard. Text durability and commit interception remain P5 work.

Every allowed incoming message revalidates current .NET authority. Idle connections are revalidated every second; the API request timeout is three seconds and failures close the socket. Revocation/expiry/feature disable therefore take effect within polling plus backend latency/timeout for idle peers, and before the next allowed application message. P5 must perform a fresh check serialized with each durable commit; this authorization check alone is not a transaction fence for future writes.

Local setup, endpoint contracts, secret/key-ring configuration and reproducible verification are in [the transport README](../WriterApp.Collaboration/README.md). Tests exercise actual Kestrel, SQLite/SQL Server and pinned-provider WebSocket connections with synthetic records. Product editor activation, native WebViews, hosted deployment, availability/load, membership, awareness and durable commits are not established by Prompt 4.

## 13. Prompt 5 implementation: commit before apply

`CollaborationCommitService` implements the private lease, append, checkpoint and storage-health boundary. It uses the existing ledger/receipt/snapshot/outbox/page tables, with an additive `CommitAllowed` grant on sessions in both providers. Commit flags default off in .NET and Node. A new explicit owner request can mint a grant; old read-only sessions cannot be promoted. Purpose-v2 tickets include the grant, and older tickets need owner refresh. Hocuspocus scope remains read-only regardless of this separate custom-channel permission.

`WriterApp.Collaboration/src/commits.mjs` owns per-room serial order. Only a strict `commitUpdate` stateless envelope can enter that path; normal sync-step-2/update frames, awareness writes and arbitrary stateless commands stay blocked. Installation and room must match the authenticated session. A bounded temporary copy must have complete Yjs dependencies and pass the common schema/JSON validation before persistence. The validator is bundled from `WriterApp.Client/src/collaboration/server-schema.ts`, with the same schema/fingerprint source as both editors, and uses the service's external pinned Yjs. Limits are 512 KiB binary per update, 1 MiB wire frame, 16 MiB resulting state and 32 admitted room operations; network buffering/rate/load acceptance remains P10 work.

The backend reauthorizes under a serializable document/session/page barrier that participates with P2 lifecycle fences and session refresh/revocation. It clears preflight tracking to prevent EF entitlement identity-map reuse. The transaction derives attribution, checks active worker/epoch/expiry and expected predecessor, then appends update, receipt and outbox together with sequence advancement. The independent receipt key remains `(page, generation, installation, updateId)`: identical bytes return the same receipt; conflicting identity reuse is rejected. A failed transaction leaves no partial prefix. Internal endpoints trust Node for Yjs/schema interpretation and independently validate byte hashes/limits and current access/order; service credentials remain private.

Node mutates/broadcasts only after that transaction commits, and sends a checked receipt after successful apply. An uncertain response or apply/receipt inconsistency quarantines the room. Recovery reads the persisted prefix and retries the same immutable envelope. A real test kills a separate Node process after .NET persistence but before apply/receipt, waits for lease expiry, and starts a new worker to prove this recovery path on both database providers. Additional fault tests cover before persistence, after apply, append rollback and snapshot rollback.

Leases last 30 seconds, bind a fresh process UUID and monotonic epoch, renew through the room queue and cannot renew an expired epoch. Takeover fences the prior writer; a restart can therefore wait up to the lease lifetime. Checkpoints run in the same room queue/lease and atomically insert a snapshot, advance the pointer and remove covered update rows. Receipts, outbox events and old snapshots remain retained. Node checkpoints every 64 commits (2 in tests). No retention deletion, projection worker or HTML write exception is implemented.

Health endpoints distinguish process liveness, recent authorized database/schema readiness and actual per-envelope durability. `onSynced` is still only transport state. A durable receipt does not assert projection freshness. The rebuilt editors retain their independent live gate and advertise no collaborative write capability. P6 owns local atomic envelope/receipt journals and account fencing; P7 owns migration and consistent consumers. See [implementation status](realtime-implementation-status.md) and [transport contracts](../WriterApp.Collaboration/README.md) for evidence and current operational limits.

## 14. Prompt 6 implementation: one local checkpoint/outbox boundary

Web uses an application-owned IndexedDB aggregate instead of independent y-indexeddb and outbox transactions. `journal.ts` scopes and hashes one versioned checkpoint/pending/receipt record, with strict transactional compare-and-swap writes and cross-tab notifications. `DeviceCollaborationJournal` uses the same DTOs through shared native atomic file replacement and a process-exclusive lease. Both retain original data on unsupported schema/version, corruption, quota/capacity or revision failure. Receipts and pending removal share a commit; failed writes cannot report locally saved.

`JournaledSession` captures a checkpoint at the local transaction's update event, not when its asynchronous writer later executes. A remote write merges from persisted checkpoint state, preserving the invariant that every uncommitted local edit represented there has an envelope. Stale-tab retries merge Yjs state and retain the same immutable identity. Network delivery uses a separate initially empty provider document containing only committed server state; uncommitted editor/journal state never reaches ordinary sync/update frames. Durable stateless envelopes replay in persisted order, and exact receipts must be stored before pending removal. Sync alone is not saved.

Known compatible generations open offline without reseeding. A fresh installation can read a validated binary baseline through authenticated sync before journal initialization. An ephemeral bootstrap read ticket does not own a local envelope; the actual installation UUID is durable before any commit. HTML reconstruction and automatic old-generation conversion are absent. Storage failure retains the previous aggregate and in-memory binary recovery state; disposal refuses to discard that state. Explicit private-recovery reasons prevent automatic delivery until fresh authorized retry.

Web account leases use authenticated owner/backend/environment and host authentication generation. Cross-tab messages invalidate but cannot authenticate a different owner. Native bindings verify the server owner against the current device account, capture `DeviceAccountService.Generation`, expose immediate `Invalidated`, and check reads/tickets/receipts/completions. Already-captured local work can finish only in its old namespace. An explicit cold-offline private-recovery binding can open known data while signed out but cannot mint network tickets; sign-in fences it. Shared native DI is registered, while P7 must connect the binding event and journal to the actual migrated editor component.

Verification includes real native child-process kills around staging/replacement/receipt storage, and actual shipped web/device bundles with IndexedDB, cross-tab CAS, authenticated Hocuspocus/.NET persistence, injected transaction/quota failures and an owned browser-process kill followed by profile reopening. ## 18. Prompt 10 implementation decisions and unmet gates
